# 多语菜单安全译审

入境旅游平台让菜品翻译、食材和过敏原说明经过来源可查、带时效、可追问的审定。

针对的事故：国际游客因译文未提示**共用炸锅**而投诉；拍照翻译此前只保存了菜名和
文化故事，餐厅当天换过食用油也无人知晓，游客收藏页仍展示一周前的过敏原说明。

## 角色与边界

| 角色 | 只负责 |
| --- | --- |
| 商户 | 以 `menu_claim.json` 声明菜品与配方标识、原料、加工助剂、交叉接触、供应批次与当天经营事实（供餐时段、炸锅换油时间） |
| 译者 | 语义；机译候选只作参考 |
| 营养专业人员 | 复核过敏原与交叉接触风险（陈述事实，禁止"绝对安全"式保证） |
| 自动翻译 | 只能停留在待审候选，不产生签署、不发布 |
| 平台 | 指纹归并、唯一公开版本、分层失效、收藏有效性、复盘留痕 |

## 模块

- `contracts.py` —— 声明合同与 schema 迁移。信封六字段（`schema_version` /
  `record_id` / `domain` / `occurred_at` / `revision` / `source`）的标识与时间
  含义保持 v1 不变；v2 在信封内嵌 `menu` 节。`confidential_recipe` 为配方机密，
  仅供签署绑定，不进入公开投影。
- `workflow.py` —— 译审状态机与三方签署（译者语义 → 营养风险 → 商户事实）。
- `intake.py` —— 拍照摄入与不确定因素判定（OCR 置信、一菜多名、季节替换、售罄）。
- `catalog.py` —— 公开版本登记处：反复拍摄归一到唯一公开版本、公开投影（机密剥离）、
  更正与撤回。
- `caching.py` —— `edge_cdn` / `app_cache` / `saved_store` 三层缓存，
  更正与撤回应逐层传播，并记录每层的**实际失效时间**。
- `saved.py` —— 游客收藏：每次查看对照当前版本与供应窗口，标出
  current / pending / superseded / withdrawn / expired。
- `visitor.py` —— 游客侧多语视图：共用炸锅等交叉接触提示、换油与供应时效、
  追问入口；待核实版本不展示任何确定安全结论。
- `review.py` —— 审核复盘包：原图指纹、配方版本、翻译链（机译+人工）、
  三方签署、状态轨迹与缓存失效记录聚合在一次展示中。

## 状态机与迁移规则

```
captured ──机译──▶ candidate ──译者──▶ in_review ──营养──▶ in_review ──商户──▶ in_review
                                                                          │
                        ┌─────────────────────────────────────────────────┤
                        ▼                                                 ▼
              held_uncertain（待核实+追问，无确定结论）            published（唯一公开版本）
                        │ 不确定因素解除后可转发布                    │
                        └──────────────────────────────▶ published     │
                                                            │ 更正（更高 revision）
                                                            ▼
                                                        superseded（旧版本留痕失效）
                                                            │ 紧急撤回
                                                            ▼
                                                        withdrawn（下架，无新版本）
```

新增状态或字段时必须遵守：

1. 既有标识与时间含义不得重解释；schema 升级在 `migrate_envelope` 中显式迁移
   （v1 → v2：六字段原样保留，`menu` 置空，不凭空补造声明）。
2. 更正必须以更高的 `revision` 新开译审单并重新三方签署；旧版本不就地改写，
   只标记 `superseded` 并进入历史。同 revision 只允许"挂起 → 确认"，不允许
   覆盖已确认版本。
3. 季节替换、临时售罄、一菜多名、OCR 置信不足任一存在，发布结果只能是
   `held_uncertain`：不拼确定安全结论，并保留开放追问。
4. 撤回无后继版本；撤回与更正都必须触发三层缓存失效，实际失效时间以
   `CacheBus.invalidation_log` 为准（离线设备可能晚于发起时间生效）。

## 数据样例

`fixtures/menu_claim.json` 是一条脱敏业务样例（炸豆腐：含大豆/小麦/花生、
与虾类共用炸锅、当天 11:30 换油、含一项机密配料）。机密节的配比与步骤已封存，
公开投影只保留该配料的过敏原风险标签（`house ingredient (recipe not disclosed)`）。

## 本地检查

运行 `python -m unittest discover -s tests`（44 个用例，覆盖合同迁移、
状态机、摄入不确定判定、唯一公开版本、分层失效、收藏有效性、游客视图、
复盘包与共用炸锅投诉端到端链路）。
